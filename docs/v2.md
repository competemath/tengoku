# Dataset version 2, and migrating from version 1

The dataset release (`vX.Y.Z`, [releases](releases.md)) is the one versioned thing a consumer downloads: the papers that cite it, the researchers and provers that retrieve from it, Tengai and Tenro.
(The CompeteMath site's import reads the repository's `data/` records, not the dataset: see "What each reader does".) Version 1 is the `1.0.0` release. Version 2 is the next major one: a different **schema**, with a migration that is a pure function of version 1
(`scripts/v2.py`). Nothing here changes the Lean tree or any pin: a consumer that pins a commit is not touched until it moves.

> **Status.** The code, the schema and the tests are in the repository. No `2.0.0` has been published: `snapshot.yml` still cuts schema 1 by default, and a maintainer cuts 2.0.0 on purpose
> (the last section). The numbers below were measured on the real `1.0.0` release by `scripts/tests/test_v2.py` (the `v2-migration` workflow).

## What version 1 gets wrong

| Finding in `1.0.0` (198,172 records) | Consequence |
| --- | --- |
| 14,911 pairs (library, name) are shared by 51,436 records; no field is a key | A consumer cannot say which record it means. `snapshot.py` compares releases by name, so the release notes' "added", "retracted" and "corrected" counts collapse records that share a name |
| 6,998 names are cut at the first non-ASCII character: `A` for `A₂_mem_circumsphere`, `Affine.CoordinateRing.mk_` for `Affine.CoordinateRing.mk_ψ₂_sq` | The published name is wrong for 3.5% of the records; the true name is only in the statement |
| `credit`, `credit_corrected_evidence` and `upstream` are null in every row | Three of twelve fields carry nothing, and `credit_corrected_evidence` is a clumsy name for the one that will carry something |
| `name` is the name as written in the source, relative to its namespace (`add_comm`, not `Nat.add_comm`) | Looking up a qualified name finds nothing |
| the statement's identity ([isnad](isnad.md)) is not in the dataset | A statement that appears under several names or libraries cannot be seen as one, which is what [tawatur](tawatur.md) counts |

## What version 2 is

One JSON object per line, as before; `snapshot.json` says `"schema": 2` (version 1 has no such key). A field that does not apply is **left out**, not null.

| Field | Version 2 | Relation to version 1 |
| --- | --- | --- |
| `schema`, `status` | `2`, `"trusted"` | new (the dataset holds trusted records only; the field is there for the day it holds more) |
| `ref` | `<library>:<name>`, or `<library>:<name>~<tag>` when that pair is shared, where `<tag>` is 10 hex digits of the statement's digest (`.2`, `.3` when even the statement ties) | new: **the key**. Unique, and a function of the data alone, so every reader computes the same refs |
| `id` | the isnad statement id | new, optional: present when the id is known (`--ids`) |
| `name` | the name the statement declares | **repaired**: version 1's name where it was complete, the header's where version 1 had cut it |
| `legacy_name` | what version 1 said | new, optional: only on the repaired records |
| `module` | the Lean module of the source file (`Mathlib.Algebra.Basic`) | new, optional: when `source_url` points into a `.lean` file |
| `library`, `statement`, `proof`, `source_url`, `licence`, `credit`, `toolchain`, `promoted_at`, `headline`, `upstream` | unchanged | `null` and `false` are left out |
| `credit_evidence` | the evidence for a corrected credit | **renamed** from `credit_corrected_evidence` |

[schemas/dataset-v2.schema.json](../schemas/dataset-v2.schema.json) is the machine form. It is a different file from `schemas/record.schema.json`, which is the schema of `data/` records.

Two properties hold for every dataset, and `v2.py check` verifies them: refs are unique, and a record that has a `legacy_name` has a name that begins with it.

### A ref is stable while what it names is

A plain ref (`mathlib:foo`) names the only record called `foo`. If a second record called `foo` arrives, both get a tag, so the first record's ref changes: the next release's migration record
([diff](#the-migration-record)) says `renamed`, and nothing is silently re-pointed. A tagged ref changes only when the record's statement does. The rule is the price of a key that needs no registry; a
fully qualified name (below) would remove most of it.

## How it fits CompeteMath's and Tengai's goals

* **Identity is the statement, not the name.** CompeteMath's provers and its search want one fact once, with every independent source for it; Tengai's canonical form and the [tawatur](tawatur.md) status are about
  statements. Version 2 carries the isnad id where it is known and makes every record addressable without one.
* **A version change is a lens.** Tengai's [ADR-0003](https://github.com/competemath/tengai/blob/main/docs/adr/0003-lens-model.md) says a version change is an isomorphism up to a stored residual. Here the residual is explicit and small:
  `downgrade(upgrade(r)) == r` for every one of the 198,172 records of `1.0.0` (no information is lost: the three dropped fields are null, the repaired names are kept as `legacy_name`), and what version 2 adds
  (`ref`, `module`, the repaired name) is a function of the data. The same lens runs in both directions, so a consumer can keep reading version 1 shapes while it moves.
* **Nothing is guessed.** A name that several records share resolves to a list of candidates, never to one of them. A rename is recorded only when exactly one successor has the same id or the same statement
  once the record's own name is taken out; otherwise the record is `removed` and the other `added`.
* **Pins protect.** Moving to a release is the consumer's act; the migration is what makes that act safe.

## Migrating

One entry point, `migrate`, which decides what it was given:

```bash
python3 scripts/v2.py migrate snapshot-dir-or-dataset --out tengoku-dataset-v2.jsonl.gz   # a version 1 snapshot or dataset file -> version 2 (a version 2 input comes back unchanged)
python3 scripts/v2.py migrate src/ --map migration.jsonl --out src-migrated/                 # Lean sources: renamed names rewritten, everything else reported
python3 scripts/v2.py migrate Nat.add_comm --out tengoku-dataset-v2.jsonl.gz                 # a name, a ref or a statement id: what it names in that dataset
python3 scripts/v2.py check tengoku-dataset-v2.jsonl.gz                                      # the invariants
python3 scripts/v2.py diff old.jsonl.gz new.jsonl.gz --out migration.jsonl                   # what a version change did to every record
```

The same from Python (`scripts/v2.py` has no dependencies):

```python
import v2
rows, report = v2.upgrade_dataset(v2.read_jsonl(path))          # version 1 rows -> version 2 rows (the refs need the whole dataset)
old_shape = [v2.downgrade(r) for r in rows]                       # and back: a consumer can keep its version 1 code while it moves
idx = v2.Index(rows)
idx.resolve("mathlib:Adj.symm~257d65b823")                        # exact
idx.resolve("A")                                                  # version 1's cut name: its candidates
idx.resolve("Nat.add_comm")                                       # a qualified name: candidates, not an answer (names are relative)
idx.ref_of_v1(old_record)                                         # the ref of a version 1 record of this dataset
```

What the migration guarantees, each one a test in `scripts/tests/test_v2.py`:

| Guarantee | Checked on |
| --- | --- |
| `downgrade(upgrade(r)) == r` | 200 seeded random datasets, and all 198,172 records of `1.0.0` |
| refs are unique, and the same data gives the same refs in any order | random datasets in shuffled order; `1.0.0` |
| the output obeys `check` | every migration the tool makes, before it writes anything |
| migrating is deterministic (the same bytes) and idempotent (a version 2 input is returned unchanged) | random datasets; `1.0.0` |
| every version 1 name still resolves, to its record or to the candidates | 3,000 records of `1.0.0` |
| a dataset compared with itself has no change; every record of two datasets is accounted for exactly once | random pairs of datasets |
| in Lean sources, a rename touches code only (not comments, docstrings, strings, longer names, `Ns.name`), and migrating twice changes nothing | hand-written and random sources |
| a version 2 dataset never turns back into schema 1 | `snapshot.py` |

### The migration record

`diff` classifies every record of a version change (the proposal in [migration support](migration-support.md), for a dataset instead of a tree): `unchanged`, `corrected` (another proof, credit, licence or toolchain),
`moved` (another module), `renamed`, `restated` (another statement under the same name), `removed`, `added`. An upstream commit bump and a promotion date are not changes. Lean sources are
migrated from this record: a renamed name is rewritten, a removed or restated one is reported with its line and left alone, and a name that several records share and that did not end up the same everywhere is
reported as `ambiguous`.

## What each reader does

| Reader | Version 1 | Version 2 |
| --- | --- | --- |
| A paper that cites `v1.0.0` | still valid: a published release is never changed | cite `v2.0.0` for the new schema; `v2.py migrate` turns the dataset it used into the new one |
| The CompeteMath site's import (`scripts/import-tengoku.ts`) | reads the `data/{tentative,trusted}/*.jsonl` records of the repository (schema `record.schema.json`), not the dataset | **unaffected**. Its own comment says a harvested statement has "no natural unique id" across re-harvests: `ref` and `id` are that key, if the import ever wants one |
| The search API ([api](api.md)) | its documented fields | unaffected: this release does not touch it |
| Provers that retrieve from the downloaded dataset | `statement` and `proof` | unchanged |
| Tengai and Tenro | pin a commit | use `ref` as the record key and `id` for the statement; the lens is [Tenro's `tools/lens`](https://github.com/competemath/tenro) |

## What this does not do

* It does not give **fully qualified names**. `name` is as written, relative to its namespace; 13,714 pairs (45,943 records) of `1.0.0` stay shared after the repair and carry a tag. A qualified name comes from the
  compiled tree (`tengoku-isnad` prints full names); `v2.py migrate --ids` takes a table of library, name and id to attach ids, and a later release can add the qualified name the same way.
* It does not compute isnad ids. A `2.0.0` cut without `--ids` has no `id` fields: the field is optional so that the cut does not wait for the id index.
* It is not smaller: `ref` and `module` repeat what `source_url` and the name say, and the compressed dataset grows by about 10% (19.7 MB against 18.0 MB for `1.0.0`).
* It does not change the Lean tree, the tiers under `data/`, or the merge queue. The tree-level migration record (`data/migrations/`, a PR class) in [migration support](migration-support.md) is still a proposal.

## Cutting 2.0.0

When the maintainer decides: `gh workflow run snapshot.yml -f schema=2` on `main`. After that the monthly run keeps schema 2 (its default is the previous release's schema), and refuses to go back to 1. `snapshot.py` compares the new dataset with the previous release record by record (reading version 1 as version 2), so the release notes
say what was added, retracted and corrected and not what the schema change did, calls the release major, and says how to migrate. The `v2-migration` workflow (manual) shows the whole thing on the real data first:
it migrates `1.0.0`, runs every test on it, and builds the dataset and release notes `2.0.0` would have from `main`, as artifacts, publishing nothing.
