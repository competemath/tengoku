# Dataset version 2, and migrating from version 1

The dataset release (`vX.Y.Z`, [releases](releases.md)) is the one versioned thing a consumer downloads: the papers that cite it, the researchers and provers that retrieve from it, Tengai and Tenro.
(The CompeteMath site's import reads the repository's `data/` records, not the dataset: see "What each reader does".) Version 1 is the `1.0.0` release. Version 2 is the next major one: a different **schema**, with a migration that is a pure function of version 1
(`scripts/v2.py`), and **every trusted theorem of the tree**, not only the records of the tier files (version 1 holds 198,172 theorems; version 2 would hold 520,611 on `main` of 2026-11-21, 322,439 of them arrived as modules: see
"The theorems that arrived as modules"). Nothing here changes the Lean tree or any pin: a consumer that pins a commit is not touched until it moves.

> **Status.** The code, the schema and the tests are in the repository. No `2.0.0` has been published, and `snapshot.yml` is unchanged: it still cuts schema 1 (the last section says what a maintainer needs to cut 2).
> The numbers below were measured on the real `1.0.0` release by `scripts/tests/test_v2.py` (the tests marked `RealRelease`, run with `TENGOKU_V1_SNAPSHOT` set to the release's directory).

## What version 1 gets wrong

| Finding in `1.0.0` (198,172 records) | Consequence |
| --- | --- |
| It holds the records of `data/trusted` and nothing of `data/intake`: 3 libraries of the 270 that have trusted theorems. The 322,439 theorems that arrived as modules (measured on `main`, 2026-11-21) are in no release, and the monthly run of 1 November said "unchanged" | The dataset holds 38% of what the repository calls trusted (198,172 of 520,611), and a paper citing `1.0.0` cannot name a theorem of Tau Ceti, lean-pool, Navier-Stokes or any library added since 30 September |
| 14,911 pairs (library, name) are shared by 51,436 records; no field is a key | A consumer cannot say which record it means. `snapshot.py` compares releases by name, so the release notes' "added", "retracted" and "corrected" counts collapse records that share a name |
| 6,998 names are cut at the first non-ASCII character: `A` for `A₂_mem_circumsphere`, `Affine.CoordinateRing.mk_` for `Affine.CoordinateRing.mk_ψ₂_sq` | The published name is wrong for 3.5% of the records; the true name is only in the statement |
| `credit`, `credit_corrected_evidence` and `upstream` are null in every row | Three of twelve fields carry nothing, and `credit_corrected_evidence` is a clumsy name for the one that will carry something |
| `name` is the name as written in the source, relative to its namespace (`add_comm`, not `Nat.add_comm`) | Looking up a qualified name finds nothing |
| the statement's identity ([isnad](isnad.md)) is not in the dataset | A statement that appears under several names or libraries cannot be seen as one, which is what [tawatur](tawatur.md) counts |

## What version 2 is

One JSON object per line, as before; `snapshot.json` says `"schema": 2` (version 1 has no such key). A field that does not apply is **left out**, not null.

| Field | Version 2 | Relation to version 1 |
| --- | --- | --- |
| `schema`, `status` | `2`, `"trusted"` | new (the dataset holds trusted records only; the field is there for the day it holds more) |
| `ref` | `<library>:<name>`, or `<library>:<name>~<tag>` when that pair is shared, where `<tag>` is 10 hex digits of the statement's digest (`.2`, `.3` when even the statement ties) | new: **the key**. Unique, and a function of the data alone, so every reader computes the same refs |
| `id` | the isnad statement id | new, optional: present when the id is known (`--ids`); never put on a record only because it shares a name with the one the id is about (see below) |
| `name` | the name the statement declares | **repaired**: version 1's name where it was complete, the header's where version 1 had cut it |
| `legacy_name` | what version 1 said | new, optional: only on the repaired records |
| `module` | the Lean module of the **upstream** source file (`Mathlib.Algebra.Basic`) | new, optional: when `source_url` points into a `.lean` file |
| `tree_module` | the module of the Tengoku tree that holds the theorem (`Tengoku.Tauceti.TauCeti.Algebra.Module.Torsion.Basic`: `import` it) | new, optional: on the theorems that arrived as modules |
| `via` | how Gate 2 related the tree's statement to the upstream original's: `equal` or `entails` | new, optional: on the theorems that arrived as modules |
| `proof` | the text from the `:=` on | **optional**: left out where the proof is a module of the tree and could not be read from it. Every row has a `proof` or a `tree_module` (`check` enforces it) |
| `library`, `statement`, `source_url`, `licence`, `credit`, `toolchain`, `promoted_at`, `headline`, `upstream` | unchanged | `null` and `false` are left out |
| `credit_evidence` | the evidence for a corrected credit | **renamed** from `credit_corrected_evidence` |

[schemas/dataset-v2.schema.json](../schemas/dataset-v2.schema.json) is the machine form. It is a different file from `schemas/record.schema.json`, which is the schema of `data/` records.

These properties hold for every dataset, and `v2.py check` verifies them: refs are unique; a record that has a `legacy_name` has a name that begins with it; a `tree_module` is a `Tengoku.` module;
`via` is `equal` or `entails`; every row has a `proof` or a `tree_module`.

## The theorems that arrived as modules

A library that arrives in the tree as an intake bundle (a factory run: `bump-library`, then an intake PR and extend PRs; [PR classes](pr-classes.md), sections 3 and 6) is listed in
`data/intake/<library>/manifest.jsonl`, one line per theorem the tree holds of it. A raze removes the lines of the modules it removes, so the manifest is exactly what is in the tree, and `snapshot.py --schema 2`
reads it as it reads the tier files. A manifest line becomes one row (`v2.intake_row`):

| Manifest line | Row |
| --- | --- |
| `name` (the full Lean name: `AddSubgroup.le_torsionBy_natCard`) | `name`; `ref` = `<library>:<name>` (a library's names are unique: the intake gate refuses a repeat) |
| `statement` (the declaration's header) | `statement`; and `proof`, the text that follows it in the module, read by `snapshot.declaration_proof` (below) |
| `module` (`Tengoku.Tauceti.TauCeti.Algebra.Module.Torsion.Basic`) | `tree_module` |
| `source_url` (the upstream file at a fixed commit) | `source_url`, and `module` = the upstream module (`TauCeti.Algebra.Module.Torsion.Basic`) |
| `toolchain`, `library` | the same |
| `via` | `via`: `equal` (the tree's statement is the original's type) or `entails` (the bridge `fun h => h : NewType → OldType` is accepted by the kernel: the tree's statement implies the original's; emissary's `scripts/bump/README.md`) |
| (not in the manifest) | `licence`, from `schemas/sources.json` by the longest `source_url` prefix, as for every other row; `status` = `trusted` |

What these rows do **not** have: `credit` and `promoted_at` (no manifest has them), an `id` unless `--ids` supplies one, and, for 2% of them, a `proof` (below): the proof of those is the Lean module `tree_module`,
which is in the source archive of the release of the same version: import it, or read the file. **The proof.** The manifest keeps a theorem's header exactly as its module has it, so the header is found in the module (`Tengoku.A.B` is `Tengoku/A/B.lean`), and the proof is what follows it, from the `:=` (or `where`)
to the end of the declaration. The end is where the tree's own gate says a command begins ([`schemas/command-keywords.json`](../schemas/command-keywords.json): a word at column 0 begins a command only if it is one of
these): the next command keyword, attribute list or doc comment at column 0. An indented line, a word at column 0 that is not a command (`termination_by`) and a comment inside the proof belong to the proof; a comment after
its last line does not. **Nothing is guessed**: a header that is not in the module (a generated lemma, a statement the factory normalised), that is in it twice, that does not begin a line, or that has no `:=` after it
(an equation-style definition keeps its match arms in the header) gets no `proof`. On `main` of 2026-11-21, 315,974 of the 322,439 rows (98.0%) have one: 5,712 headers are not in the module, 495 have no `:=`, 242 are in the module twice and 16
are other cases. Checked against the other source of proofs, the Mathlib records of the tier files (a slice of the seed: 23,000 records, of which the reader found 21,707 once in their module): the same proof as the app extracted for 21,495, and for
212 a proof that differs by a comment the app had dropped or by a later change to the module (the ends of the two agree in the two I read). Every one of the five proofs that contain the word `sorry` has it in a comment.

Names here are whole, not cut as version 1's were: in six manifests measured (69,252 lines) no name is a proper prefix of its header's name, and the 1,113 names among them with non-ASCII characters are complete.
322,439 rows on `main` of 2026-11-21, every one with a licence, an upstream module and a verdict; 291,749 are `equal` and 30,690 `entails`.

A library is in the tier files or in `data/intake`, never both (the intake gate refuses a library that is in the tree already; on `main` of 2026-11-21 the two sets of library names are disjoint), so the plain ref is unique;
a repeat would make two rows with one ref, which `check` refuses and the cut stops on.
The tentative and staging tiers are not in the dataset: nothing tentative is built into the tree.

### A ref is stable while what it names is

A plain ref (`mathlib:foo`) names the only record called `foo`. If a second record called `foo` arrives, both get a tag, so the first record's ref changes: the next release's migration record
([diff](#the-migration-record)) says `renamed`, and nothing is silently re-pointed. A tagged ref changes only when the record's statement does. The rule is the price of a key that needs no registry; a
fully qualified name (below) would remove most of it.

## How it fits CompeteMath's and Tengai's goals

* **Identity is the statement, not the name.** CompeteMath's provers and its search want one fact once, with every independent source for it; Tengai's canonical form and the [tawatur](tawatur.md) status are about
  statements. Version 2 carries the isnad id where it is known and makes every record addressable without one.
* **A version change is a lens.** Tengai's [ADR-0003](https://github.com/competemath/tengai/blob/main/docs/adr/0003-lens-model.md) says a version change is an isomorphism up to a stored residual. Here the residual is explicit and small:
  `downgrade(upgrade(r)) == r` for every one of the 198,172 records of `1.0.0` (no information is lost: the three dropped fields are null, the repaired names are kept as `legacy_name`), and what version 2 adds
  (`ref`, `module`, the repaired name) is a function of the data. The same lens runs in both directions, so a consumer can keep reading version 1 shapes while it moves.
* **Nothing is guessed.** A name that several records share resolves to a list of candidates, never to one of them. A rename is recorded only when exactly one successor has the same id or the same statement
  once the record's own name is taken out; otherwise the record is `removed` and the other `added`.
* **Pins protect.** Moving to a release is the consumer's act; the migration is what makes that act safe.

## Migrating

One entry point, `migrate`, which decides what it was given:

```bash
python3 scripts/v2.py migrate snapshot-dir-or-dataset --out tengoku-dataset-v2.jsonl.gz   # a version 1 snapshot or dataset file -> version 2 (a version 2 input comes back unchanged)
python3 scripts/v2.py migrate src/ --map migration.jsonl | git apply                         # Lean sources: a patch on stdout (renamed names rewritten), the report on stderr (--projections: see below)
python3 scripts/v2.py migrate Nat.add_comm --out tengoku-dataset-v2.jsonl.gz                 # a name, a ref or a statement id: what it names in that dataset
python3 scripts/v2.py check tengoku-dataset-v2.jsonl.gz                                      # the invariants
python3 scripts/v2.py diff old.jsonl.gz new.jsonl.gz --out migration.jsonl                   # what a version change did to every record
```

A path on the command line must lie in the working directory or the temporary directory (resolved first, so `..` and symlinks do not get out): the rule of `scripts/ci/axiom_scan.py`. The tool writes only `--out` of a dataset
migration and of `diff`; Lean sources are never written, the change is a patch.

The same from Python (`scripts/v2.py` has no dependencies):

```python
import v2
rows, report = v2.upgrade_dataset(v2.read_jsonl(path))          # version 1 rows -> version 2 rows (the refs need the whole dataset)
old_shape = [v2.downgrade(r) for r in rows]                       # and back: a consumer can keep its version 1 code while it moves
idx = v2.Index(rows)
idx.resolve("mathlib:Adj.symm~257d65b823")                        # exact
idx.resolve("A")                                                  # version 1's cut name: its candidates
idx.resolve("Nat.add_comm")                                       # a qualified name: candidates, not an answer (names are relative)
idx.ref_of_v1(old_record)                                         # the ref of a version 1 record of this dataset
```

What the migration guarantees, each one a test in `scripts/tests/test_v2.py`:

| Guarantee | Checked on |
| --- | --- |
| `downgrade(upgrade(r)) == r` | 200 seeded random datasets, and all 198,172 records of `1.0.0` |
| refs are unique, and the same data gives the same refs in any order | random datasets in shuffled order; `1.0.0` |
| the output obeys `check` | every migration the tool makes, before it writes anything |
| migrating is deterministic (the same bytes) and idempotent (a version 2 input is returned unchanged) | random datasets; `1.0.0` |
| every version 1 name still resolves, to its record or to the candidates | 3,000 records of `1.0.0` |
| a dataset compared with itself has no change; every record of two datasets is accounted for exactly once | random pairs of datasets |
| in Lean sources, a rename touches code only (not comments, docstrings, strings, longer names, `Ns.name`), and migrating twice changes nothing | hand-written and random sources |
| a version 2 dataset never turns back into schema 1 | `snapshot.py` |

### Ids, and names that several records share

`--ids` takes a TSV of `library`, `name`, `id` and, optionally, `module`. An entry with a module goes to the record of that module. An entry without one goes to a record only when its (library, name) is not shared in the dataset:
an id says what a statement *is*, and the other records of a shared name state other things. The report counts the records where an id was refused for that reason (`ids_skipped_shared`). An entry listed with two different
ids has none.

### The migration record

`diff` classifies every record of a version change (the proposal in [migration support](migration-support.md), for a dataset instead of a tree): `unchanged`, `corrected` (another proof, credit, licence or toolchain),
`moved` (another module), `renamed`, `restated` (another statement under the same name), `removed`, `added`. An upstream commit bump and a promotion date are not changes. Lean sources are
migrated from this record: a renamed name is rewritten in code only (not in comments, docstrings, strings or character literals), a removed or restated one is reported with its line and left alone, and a name that several
records share and that did not end up the same everywhere is reported as `ambiguous`.

A dotted name that only *begins* with a changed name (`old_name.symm`, `old_name.trans h`) is **`unjudged`**: it may be the name used with a projection or a different declaration under it, and a file cannot say which.
It is reported with the head and what happened to it and left as it is. `--projections` rewrites the head of a renamed one: right for `.symm` and `.mp`, wrong when `old_name.sub` is a declaration of its own, so it is a choice.
A name that only *ends* with a changed name (`x.old_name`) is not an occurrence, and a short name used under `open` is not seen at all.

The release notes of a schema 2 release are built from the same record, not from the refs: a second record of a name gives both a tag, and the notes say `Renamed` for the first, not `Retracted`. Where the old ref cannot be
assigned to one successor (two records that state the same thing) the notes say `Retracted` and `Added` and nothing else, never a guess.

## What each reader does

| Reader | Version 1 | Version 2 |
| --- | --- | --- |
| A paper that cites `v1.0.0` | still valid: a published release is never changed | cite `v2.0.0` for the new schema; `v2.py migrate` turns the dataset it used into the new one |
| The CompeteMath site's import (`scripts/import-tengoku.ts`) | reads the `data/{tentative,trusted}/*.jsonl` records of the repository (schema `record.schema.json`), not the dataset | **unaffected**. Its own comment says a harvested statement has "no natural unique id" across re-harvests: `ref` and `id` are that key, if the import ever wants one |
| The search API ([api](api.md)) | its documented fields | unaffected: this release does not touch it |
| Provers that retrieve from the downloaded dataset | `statement` and `proof` | unchanged |
| Tengai and Tenro | pin a commit | use `ref` as the record key and `id` for the statement; the lens is [Tenro's `tools/lens`](https://github.com/competemath/tenro) |

## What this does not do

* It does not give **fully qualified names** to the records of the tier files. Their `name` is as written, relative to its namespace; 13,714 pairs (45,943 records) of `1.0.0` stay shared after the repair and carry a tag. A qualified
  name comes from the compiled tree (`tengoku-isnad` prints full names); `v2.py migrate --ids` takes a table of library, name and id to attach ids, and a later release can add the qualified name the same way. The rows of
  the theorems that arrived as modules already have full names.
* It does not give every theorem that arrived as modules a `proof` text: 2% have none (the reasons are above), and their proof is `tree_module`, in the source release. It does not run Lean: the text is the module's, not a
  re-elaboration of it.
* It does not compute isnad ids. A `2.0.0` cut without `--ids` has no `id` fields: the field is optional so that the cut does not wait for the id index.
* It is not smaller. For the same 198,172 records `ref` and `module` repeat what `source_url` and the name say, and the compressed dataset grows by about 10% (19.7 MB against 18.0 MB for `1.0.0`). With the tree and its proofs it is
  71.0 MB compressed for 520,611 rows (measured on `main` of 2026-11-21: 59 s and 4.1 GB of memory to build; without the proofs 38.9 MB).
* It does not change the Lean tree, the tiers under `data/`, or the merge queue. The tree-level migration record (`data/migrations/`, a PR class) in [migration support](migration-support.md) is still a proposal.

## Cutting 2.0.0

`python3 scripts/snapshot.py --schema 2 --previous <dir of the 1.0.0 release> --out out --notes notes.md` builds the dataset, manifest and release notes `2.0.0` would have from `main`, and publishes nothing. On `main` of 2026-11-21
(`257dacb`) it said `v2.0.0: 520611 trusted records` (198,172 from the tier files, 322,439 from the manifests of 267 libraries, 315,974 of those with a proof read from their module), `v2.py check` found no problem in them, and the notes said Added 322,439, Retracted 0, Corrected 0. It compares the new dataset with
the previous release record by record (reading version 1 as version 2), so the notes say what was added, retracted, renamed and corrected and not what the schema change did, call the release major, and say how to migrate; a dataset
never goes back to schema 1.

What is not in this change: `snapshot.yml` still passes no `--schema`, so the monthly run and a manual run cut schema 1, and a release can be cut as schema 2 only by changing that workflow. A workflow change is proven on the
sandbox first ([CONTRIBUTING](../CONTRIBUTING.md), `scripts/ci/campaign/README.md`), so it is a separate change: a `schema` input (`keep` by default, which follows the previous release's schema so the monthly run cannot go back
from 2 to 1) and a manual workflow that runs the real-data tests and builds the preview as artifacts.
